# التشغيل والنشر والنسخ الاحتياطي

## الوضع المحلي

`npm.cmd run dev` يشغل الواجهة والخلفية معًا. `npm.cmd run build` ثم `npm.cmd start` يشغل النسخة المبنية على المنفذ 3000 بخادم واحد. إعدادات الخلفية في `backend/.env` ولا تدخل ضمن الصور أو ملفات النشر.

التحديثات الحالية تُطبق باستخدام `npm.cmd run migrate`. المخطط الأساسي مطلوب لقواعد البيانات الجديدة فقط. لا تُعد تطبيق `schema.sql` على قاعدة بيانات التشغيل.

## تشغيل قاعدة البيانات والتخزين وRealtime على Supabase

يحفظ التطبيق بيانات المزاد في المخطط الخاص `mazad`، ويستخدم جلسات Express والحسابات الحالية. يحافظ هذا الفصل على جداول Supabase Auth الموجودة في `public`. تفعيل Supabase Auth لحسابات الموقع يحتاج ترحيلًا مستقلًا للهويات والجلسات.

بعد نقل قاعدة البيانات إلى `mazad`، أضف `DATABASE_URL` لاتصال Session pooler و`DB_SCHEMA=mazad` و`SUPABASE_URL` ومفتاح الخادم `SUPABASE_SECRET_KEY` إلى `backend/.env`. يدعم الخادم أيضًا المفتاح القديم عبر `SUPABASE_SERVICE_ROLE_KEY`. اتصال PostgreSQL يتحقق من شهادة TLS. عند استخدام شهادة جذر خاصة، حدّد مسارها في `DB_SSL_CA_PATH` نسبةً إلى مجلد `backend`.

```powershell
npm.cmd run connect:supabase
```

يتحقق الأمر من المخطط، ويجهز حاويتَي التخزين الخاصتين `mazad-cars` و`mazad-documents`، وينقل الملفات المرتبطة بالسجلات من `uploads` ويتحقق من بصماتها، ثم يختبر بث Realtime. أعد تشغيل التطبيق بعد نجاحه. يمكن إعادة الأمر عند انقطاع النقل. احتفظ بملفات المصدر حتى اكتمال التحقق.

روابط الصور والمستندات تمر عبر الخادم. تفحص مسارات المستندات صلاحيات الإدارة أو إتاحة أوراق المزاد قبل جلب الملف. يحوّل الخادم بث Supabase الخاص إلى إشارات تحديث عامة عبر `/api/realtime/events`، وتقرأ الواجهة بياناتها عبر API بصلاحيات الجلسة. مصدر إشارة التحديث لا يحمل سجلات أو بيانات حسابات. يبقى التحديث الدوري متاحًا عند انقطاع الاتصال الفوري.

RLS مفعّل على جداول `mazad`، مع منع الوصول لأدوار المتصفح. يستخدم التشغيل حساب `mazad_server` بسياسات مخصصة للخادم وصلاحيات البيانات داخل هذا المخطط. يتطلب تطبيق التحديثات البنيوية ضبط `DATABASE_ADMIN_URL` بحساب مالك قاعدة البيانات. في إعدادات الاستضافة استخدم متغيرات التشغيل نفسها، وأبقِ استضافة Express عاملة لتشغيل عامل إغلاق المزادات.

الاختبارات المعزولة تستخدم اتصال PostgreSQL المحلي المحدد بمتغيرات `DB_*`. يمكن تخصيص قاعدة اختبار أخرى عبر `TEST_DATABASE_URL`، بحساب يستطيع إنشاء مخططات مؤقتة.

النسخة المحلية تنسخ مخطط التطبيق وملفات `uploads` الموجودة على الجهاز. عند استخدام عدة خوادم، جهّز نسخة مستقلة كاملة لملفات Supabase Storage، لأن كل خادم يحتفظ بنسخ الملفات التي رفعها محليًا.

## نسخة احتياطية محلية

```powershell
npm.cmd run backup
```

ينشئ مجلدًا مستقلًا داخل `backups` يضم `database.dump` بصيغة PostgreSQL custom، ومجلد الصور `uploads` وملف `manifest.json`. يستخدم `pg_dump` المثبت محليًا؛ على Windows يبحث داخل مجلد PostgreSQL في Program Files. يمكن تحديد المسار صراحة بواسطة `PG_DUMP_PATH` والمكان بواسطة `BACKUP_DIR`.

قاعدة البيانات والصور تُنسخان بالتتابع؛ خذ النسخة خلال فترة لا يجري فيها تعديل الصور للحصول على مجموعة متسقة. المجلدات التي تبدأ بـ `.pending-` تعني أن النسخ لم يكتمل، ولا تعتبرها نسخة صالحة. ملفات البيئة وكلمات المرور ليست ضمن ملفات إعدادات النسخة، لكن ملف قاعدة البيانات نفسه يحتوي بيانات الحسابات والجلسات، لذلك احفظه في مكان محدود الوصول.

افحص قائمة محتويات النسخة بأداة `pg_restore --list path/to/database.dump`. للاستعادة، أنشئ قاعدة بيانات فارغة جديدة ثم استخدم `pg_restore --no-owner --no-acl --dbname new_database path/to/database.dump`، وانسخ `uploads` إلى مكان الصور. اختبر الحسابات والصور على القاعدة الجديدة قبل تغيير اتصال التشغيل. احتفظ بسر الجلسة وبيانات الاتصال في مخزن منفصل آمن.

## النشر باستخدام Docker

الملفات جاهزة في `Dockerfile` و`deploy/compose.yml`. هذا المسار يحتاج Docker وخادمًا عامًا ودومينًا موجهًا إليه. لا تغيّر إعدادات قاعدة البيانات المحلية عند تجهيز الخادم.

1. انسخ `deploy/.env.example` إلى `deploy/.env` وأدخل الدومين الحقيقي وكلمتي مرور مختلفتين لمالك قاعدة البيانات وحساب التطبيق، وسر جلسة عشوائيًا.
2. من مجلد المشروع شغّل `docker compose -f deploy/compose.yml --env-file deploy/.env config --quiet` لفحص الإعدادات.
3. شغّل `docker compose -f deploy/compose.yml --env-file deploy/.env up -d --build`.
4. افتح الدومين باستخدام HTTPS. Caddy يستقبل الاتصال العام، والتطبيق وقاعدة البيانات داخل شبكة Docker دون نشر منفذيهما للعامة.

عند أول تشغيل فقط، تُنشأ قاعدة البيانات وتُطبق التحديثات ويُنشأ مستخدم `mazad_app` بصلاحيات البيانات دون صلاحيات إنشاء الجداول أو إدارة الأدوار. يتصل التطبيق بهذا المستخدم. لتهيئة مدير، أنشئ حسابًا من الموقع ثم شغّل أداة `scripts/grant-admin.js` داخل حاوية التطبيق مع `ADMIN_EMAIL` أو `ADMIN_PHONE`.

إذا كانت لديك بيانات محلية تريد نقلها، استخدم نسخة احتياطية واستعادة مقصودة إلى قاعدة فارغة ثم راجع منح صلاحيات `mazad_app`. ملفات Compose تبدأ قاعدة جديدة ولا تنقل بيانات جهازك تلقائيًا. لا تستخدم حذف وحدات التخزين كطريقة لترقية قاعدة موجودة.

للتحديثات اللاحقة، خذ نسخة احتياطية أولًا، ثم طبّق ملفات migrations الجديدة بحساب مالك قاعدة البيانات من حاوية `db`، ثم أعد بناء التطبيق. ملفات `database/` مركبة للقراءة داخل `/mazad-database` في حاوية قاعدة البيانات.

لأخذ نسخة داخل Docker:

```text
docker compose -f deploy/compose.yml --env-file deploy/.env --profile tools run --rm backup
```

تُحفظ في مجلد `backups` على المضيف. الأمر ينشئ نسخة عند تشغيله؛ لا يوجد جدول نسخ تلقائي مفعل.

## السجلات والمراقبة

طلبات API تسجل بصيغة JSON مع رقم مرجعي ومدة وحالة HTTP، دون تسجيل كلمات المرور أو أجسام الطلبات. `/api/health` يتحقق من اتصال PostgreSQL. يمكن قراءة سجلات الحاويات باستخدام `docker compose logs` ومراقبة حالة الصحة.

تستخدم جلسات الإنتاج cookies آمنة، وتوجد سياسة CSP ورؤوس أمان. يفترض `trust proxy=1` أن التطبيق خلف وكيل واحد موثوق، كما في إعداد Caddy المرفق. حافظ على عدم نشر منفذ التطبيق للعامة في هذا الوضع.

## حالة التحقق

دورة الحسابات والسيارات والمزادات والفواتير والإشعارات مغطاة باختبار تكامل على مخطط مستقل. البناء والتنسيق وفحص ملف النسخة الاحتياطية المحلي تُجرى على الجهاز. إعداد Docker وHTTPS يحتاج التحقق على خادم النشر؛ لم يُشغّل Docker على هذا الجهاز لعدم تثبيته.

الدفع بالمحفظة افتراضي تجريبي دون أموال حقيقية. الدفع اليدوي متاح للمزادات السابقة أو عند اختياره صراحة. تأكيد الهاتف واستعادة كلمة المرور عند نسيانها والإشعارات الخارجية تحتاج ربط SMS أو بريد أو بوابة دفع فعلية. لا توجد رسائل أو مدفوعات تجريبية يُعرض نجاحها وكأنها أُرسلت أو سُددت فعلًا.

عامل الإغلاق الدوري يبدأ مع backend/server.js، ويعيد فحص وقت كل مزاد بعد القفل لحماية التمديد المتزامن. يبدأ أيضًا عند إعادة تشغيل الخادم، فيعالج المزادات التي انتهت أثناء توقفه. يجب إبقاء خدمة الخلفية عاملة لتنفيذ الإغلاق خلال خمس ثوانٍ تقريبًا.

ينفذ العامل نفسه انتهاء مهلة سداد الفائز وفك الحجوزات. عند تطبيق التحديث 012 تبقى المدفوعات السابقة كما كانت، وتُمنح الفواتير المعلقة التي لم يكن لها موعد 48 ساعة من لحظة التحديث. راجع المواعيد بعد النقل وتأكد من تشغيل العامل. مجلد `uploads/private/ownership` يحتوي مستندات يجب نسخها مع الصور وقاعدة البيانات، وعدم تقديمه بواسطة Caddy أو أي تخزين عام. التطبيق يعرض الأوراق عبر مسار المزاد بعد اعتماد السيارة وأوراقها فقط، ويتيح المراجعة عبر مسار الإدارة المحمي. صور الجواز لا تعرض إلا للإدارة. النسخ الاحتياطية تتضمن المستندات ويجب تقييد الوصول إليها.
